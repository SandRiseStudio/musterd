# Tailscale transport generator — Increment 2b design

**Date:** 2026-09-15  
**Status:** proposed  
**Scope:** design only; implementation requires an ADR and approved implementation plan.

## Outcome

Increment 2b produces deterministic, secret-free Tailscale policy artifacts from the committed Team
roster, ADR 400 governed-model workload identities, and a transport manifest. It provides reviewed
transport intent for a later governed-launch increment without applying a Tailscale policy, mutating
daemon configuration, discovering nodes, or activating model enforcement.

## Boundaries

Increment 2a (ADR 400) owns the Aperture managed fragment. Increment 2b owns only portable Team
transport policy:

- workload tags and their ownership;
- exact agent Member-to-transport-node-key mappings;
- least-privilege workload-to-Aperture HTTPS reachability; and
- a rendered mapping artifact for later runtime binding.

Daemon bind address, allowed Host values, Tailscale Serve, Tailscale API credentials, device identity,
and runtime node IDs remain operator-managed facts. `musterd integration doctor --tailscale` remains
the read-only verifier for those facts.

## Inputs

The generator reads only:

```text
.musterd/team.toml
.musterd/seats/*.toml
.musterd/roles/*.toml
.musterd/governed-models.json
.musterd/governed-transport.json
```

`governed-models.json` remains the sole source of opaque workload IDs. The new strict, versioned
transport manifest declares:

- opaque `node_key` values;
- the active agent Members each key may host; and
- one exact `aperture_tag`, defaulting nowhere and failing when absent; and
- one or more explicit non-wildcard Tailscale tag owners, used for every generated workload tag.

Every active agent Member must have one workload ID and one or more declared transport-node keys.
Human and service Members cannot appear in a transport mapping. Duplicate, stale, broad, or
credential-like values fail generation.

## Artifacts and command

`musterd integration generate tailscale [--write | --check]` follows ADR 400's preview/write/check
contract. `--write` atomically replaces exactly:

```text
.musterd/generated/tailscale/
├── policy.hujson
└── workloads.json
```

The Tailscale-only renderer emits:

- explicit tag owners for `tag:musterd-agent` and each exact
  `tag:musterd-member-<workload_id>`;
- ACLs permitting each exact workload tag to reach only the declared `aperture_tag:443`; and
- a complete lexical Member mapping with in-scope and out-of-scope reasons.

Generated bytes contain no credentials, provider endpoints, runtime node IDs, machine paths,
timestamps, Presence, wildcards, broad principals, or daemon settings. They are review artifacts:
operators merge and apply them manually.

## Runtime relationship

The generated `node_key` is durable Team policy, not an authenticated machine identity. Increment 3
must bind a declared key to an enrolled daemon node through a new authorization protocol, then refuse
a governed launch when that binding, the matching generated policy, or the current transport doctor
posture cannot be proven. A node label and a caller-provided node ID are never identity roots.

## Verification

- Protocol tests reject malformed manifests, unknown/human/stale mappings, duplicate keys, broad tags,
  and secret-like text.
- Resolver and golden tests prove lexical deterministic output and exact ACL narrowing.
- CLI tests cover preview, atomic write, current/stale check, and mutually exclusive modes.
- Doctor tests preserve its read-only, operational-verification boundary; 2b does not broaden it into
  a configuration applicator.
- The terminal design brief, paved-road design, architecture, security guidance, and command catalog
  change with the implementation.

## Deferred

Tailscale API application, Tailscale device/bridge creation, daemon bind or Host configuration,
runtime Member/node binding, provider routing, governed harness launching, request authorization,
and model-enforcement activation are Increment 3 or later work.
