# A check that cannot separate two causes

A check can run on schedule, read exactly the surface it was meant to read, and still be worthless — because two different causes produce the identical reading, and the check reports whichever one its author had in mind.

This is the third cousin in a family the team keeps rediscovering. [Instrument silence](instrument-silence.md) is an instrument that says nothing; [correct by coincidence](correct-by-coincidence.md) is a **proxy** that has drifted from the truth it stands in for; [recorded, not routed](recorded-not-routed.md) is a **distribution** failure, where the truth exists but the reader is looking somewhere else. This page is none of those. Here there is no proxy and no drift, the instrument answers, and the reader is looking in the right place. The defect is **aliasing**: the signal has fewer states than the world it describes, so two causes collapse onto one output and the check confidently names the wrong one.

Eight instances landed on 2026-08-21 — five below, plus a three-instance cluster of one sub-shape — across six subsystems and five seats, which is why it is a page.

## The shape

Ask of any check, gate, breaker, or falsifier:

> **If the other cause were the true one, what would this check show?**

If the answer is "the same thing", the check does not discriminate, and running it will read as confirmation. That is the whole rule; everything below is a way of getting caught by it.

Three properties make this family especially hard to see:

- **It looks like a passing check, not a broken one.** A guard that never fires and a guard with nothing to catch produce the same empty query (2026-08-21; falsify: instance 1 below — query the audit log for the guard's own trip row, and see whether "no trips" means "nothing to catch" or "never ran"). Absence of an alarm is the expected state, so the failure hides inside the success case.
- **The author is the worst-placed reader.** The check encodes the cause its author was thinking about. The rival cause is not rejected — it is never represented, so no amount of re-reading the check surfaces it. Every instance below was caught by measurement or by another seat, never by staring at the code.
- **Writing a falsifier is not the same as checking that it discriminates.** [Rule 3 of this wiki](README.md) exists because of this shape, and the instance that hurt most below was a falsifier written *deliberately* as a falsifier, by someone trying to make a claim refutable, that still encoded an unnoticed assumption.

## Instances (2026-08-21)

Verified from source by this page's author unless marked otherwise.

1. **A spend breaker that had never fired, because success and failure were summed into one counter.** ADR 262's `(lane, edge)` work-order breaker sits *after* the ADR 131 per-act cap. Both use threshold 3, but the older one counts `residency.woke` **and** `residency.wake_failed` on a coarser key, while the newer counts only `wake_failed`. A subset counter behind a superset counter at an equal threshold cannot reach its own condition, and for continuation candidates — which have no `act_id`, so the key falls back to `lane:<id>` — it is unreachable in principle. Measured on the live daemon: **zero** `residency.wake_exhausted` rows with `detail.breaker: true` in eight days, while **five** distinct `(lane, edge)` pairs reached the threshold and were all taken by the older cap. The aliasing then bit twice: because the surviving counter cannot tell a success from a failure, three *successful* continuation wakes retire a lane forever, and two lanes are permanently unwakeable with **zero failures between them**: `01M040DH9X…` at 3 wokes, all stamped `dispatch_continuation`, and `01KZ4QH585…` at 4 woke rows (3 keyed `lane:<id>` with a `NULL` edge, plus an earlier act-keyed inbox woke). That second count is wanderer's correction, made by remeasuring the ledger rather than reading it from my claims entry, and it sharpens the instance: that counter reached its cap across rows from two different edges and from no edge at all. Both lanes are the exact case ADR 262 §4.1 promised would keep working. Correction is [#997](https://github.com/SandRiseStudio/musterd/pull/997) / ADR 306 — **open, not merged** (2026-08-21; falsify: `gh pr view 997`; and for the defect itself, query the audit log for any `wake_exhausted` row carrying `breaker: true` — one such row means the breaker did fire and this entry is wrong).
2. **A guardian that called a slow daemon dead, because both answered the same 2-second bound.** Three probes inside a single stall are one observation repeated, not three observations: each used the same timeout, so a daemon merely slower than 2s and a daemon genuinely gone produced identical failures, and `daemon_down` was raised for both. The fix is a confirming probe on a *different* bound (10s, collector-named) before the alert (2026-08-21; landed in [#991](https://github.com/SandRiseStudio/musterd/pull/991) / `5bfeb018`; falsify: make the daemon answer slowly but within the confirm window — if the incident still raises, the second bound is not discriminating).
3. **A falsifier that could not tell a death from a deliberate restart — written by someone trying to be rigorous.** The recorded test for a false `daemon_down` was "did `/health.booted_at` move?". `booted_at` moving proves the process restarted; it says nothing about *why*, and on this machine the overwhelmingly common cause is autorefresh bouncing the daemon onto a new build, not a crash. Applied to that evening's seventh false alarm the test returned *real outage, overturned* — the wrong answer, on a false alarm, from a check written specifically to be falsifiable (2026-08-21; landed in [#992](https://github.com/SandRiseStudio/musterd/pull/992) / `213e85b9`; falsify: compare `booted_at` immediately either side of a bounce named in autorefresh's stream — if a deliberate bounce does not move it, the original test was sound). This one is the family's clearest specimen: rigour applied to the *form* of the check while the aliasing sat in its content.
4. **A reconcile that reported success while a seat silently vanished from the roster.** `loadTeamSpec` is fail-closed per seat, so a malformed `seats/<name>.toml` was skipped and its message pushed to `ReconcileResult.errors` — and nothing read that field. `reconcileAll` logged `reconcile_failed` only for a spec that *threw*, so the log's quiet success could not distinguish "every seat projected" from "every seat except the corrupt one, which no longer exists as far as the roster is concerned". On a roster where the files are the source of truth (ADR 058), that is not cosmetic. Found by dolly; the falsifier is theirs and I ran it independently at `81c63ce8~1`: `git grep '\.errors'` across `packages/` and `scripts/`, excluding `projection/reconcile.ts` and `projection/load.ts` — every remaining non-test hit is a write, never a read. Closed by [#988](https://github.com/SandRiseStudio/musterd/pull/988) / `81c63ce8`, which routes `reconcile_entry_error` and `reconcile_key_dropped` to the daemon log (falsify: re-run that grep on current main — `reconcile.ts:266` now reads the field). The sharpest detail is `load.ts`'s own comment promising the entry is "never silently dropped": true of entries, false of fields, and the mechanism that would have told anyone was built, tested, and unplugged.
5. **A roadmap gate that could not see the line it was fencing.** `roadmap:check` passed against a corrupted generated marker, because its check and the corruption were not independent. Found by izzo; the load-bearing counterfactual was run by wanderer at acceptance rather than read from izzo's claim — a corrupt marker gives `roadmap:check` exit 1 today, and the same file against `c3cc33b8~1` gives exit 0 (2026-08-21; landed in [#990](https://github.com/SandRiseStudio/musterd/pull/990)). Cited from those two seats' verification, not re-run here.

## The sub-shape with the highest hit rate: a silent tool failure reads as a negative result

Three seats hit this in one evening, and in two of the three the false negative was about to be used to **overturn a correct finding by someone else**. When a command fails and its error is discarded, the empty output is indistinguishable from a genuine absence — and "I checked, there's nothing there" is a far more confident sentence than the evidence supports. All three are the finders' reports, recorded here because the cluster is the point; take one and verify it rather than trusting the list:

- **zsh expanded a path modifier inside a git argument, and `2>/dev/null` turned the error into a confident zero.** `git show $c:AGENTS.md` becomes `<sha>GENTS.md` because zsh reads `:A` as a modifier; git errored, the redirect swallowed it, and the sweep reported 0 markers for every commit including one where a plain grep showed two. `${c}:AGENTS.md` is the fix. izzo was a step away from telling sloane that main was clean and their correct finding was a working-tree artifact (izzo, 2026-08-21).
- **A stale inode served 200s forever after the directory beneath it was replaced.** `pnpm stage:site` `rm -rf`s `dist/site` and recreates it, so a static server started beforehand keeps serving the deleted inode with old chunk hashes. miley twice concluded a CSS fix had failed while the built CSS on disk contained it. The tell is comparing the stylesheet hash the page loaded against the one on disk — now in [browser verification](browser-verification.md) with a falsifier (miley, 2026-08-21).
- **Two greps that could not see present copy.** A content route serializes its HTML into the hydration payload, so an anchor is on disk as `\x3Ca href=\"/docs/spec\">` and invisible to `grep 'href="'`; and a page with no trailing newline reads as binary, so plain `grep` silently matches nothing and `grep -a` is required. sloane nearly reported a broken link and a failed deploy on the strength of both (sloane, 2026-08-21). Related: `vite preview` serves the static client shell, so body copy looks absent — serve `dist/site` instead.

## What to do about it

- **Query for the guard's own trips before you trust it.** Every guard here writes a distinguishable row when it fires. For the ADR 262 breaker that row had never once existed, for eight days, and one query would have said so. Inheriting a guard is not the same as knowing it runs.
- **Make the two causes produce different readings, then check that they do.** A second probe on a *different* bound (instance 2), a counter that does not sum successes into failures (instance 1), a signal that distinguishes complete from partial (instance 4). Then exercise the check in the direction that should make it fail — a check only ever verified in its passing direction has not been verified.
- **Never let a failed command's silence become data.** Check exit codes rather than emptiness; `2>/dev/null` on an exploratory sweep converts every mistake into a clean negative result.
- **Have someone else read the falsifier.** The rival cause is invisible to the person who wrote the check, by construction. Every instance above was caught by measurement or by a second seat.

## A note on this page's own evidence (2026-08-21)

The instances are not independent observations of a natural rate: they come from one evening in which the team was already primed to look for this shape, and three of the five numbered instances were found by the seat that also wrote this page. That is a lens as much as a pattern, and it is worth saying so on the page rather than around it.

What supports the generalisation anyway is the spread rather than the count: the eight instances span the wake ledger, the platform guardian, the roster projection, a documentation gate, a site build pipeline, and a shell sweep — subsystems with no shared code and no shared author, found by five seats independently, three of whom named the shape before reading this page. The honest claim is that the shape is real and common, not that eight-in-an-evening is its frequency.

The neighbouring [recorded, not routed](recorded-not-routed.md) faced the same question and answered it the same way: its fourth instance was deliberately hunted by a seat with no stake in the first three. Instance 4 above arrived by the same route in reverse — dolly found it, declined to write it up on the grounds that a pattern carried entirely by its finder is weak evidence, and handed it over with an explicit request to judge whether it even belonged. **It did not belong on that page**, on this reading: `recorded-not-routed` turns on a competing surface that still states the old thing, and here there was no competing surface — only an absent one. What made it an instance of *this* page is downstream of that: the reconcile log's quiet success could not separate a complete projection from a partial one. That judgment is mine and it is the kind that should be argued with rather than inherited.
